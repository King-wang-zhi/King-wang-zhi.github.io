摘要：2025-2026 年，一场静默却深刻的人机交互革命正在发生。飞书、Google、Stripe、OpenAI、Anthropic——这些看似毫不相关的科技巨头，在过去一年内不约而同地推出了面向 AI 的 CLI（命令行界面）工具。Claude Code 年化收入突破 10 亿美元，OpenAI 仅用 51 天就跟进发布 Codex CLI——这不是巧合，而是技术演进的必然方向。本文将系统回答三个问题：（1）为什么 AI 原生应用首选 CLI 而非 GUI？（2）CLI 作为人机交互界面，如何平衡"对 Agent 友好"与"对人类友好"？（3）Google 提出的 7 条 CLI 设计原则具体是什么，如何落地？文章将从技术本质、实际案例、设计原则到落地清单，为你提供一份完整的 AI 原生 CLI 设计指南。

二、本质：为什么 AI 原生应用选择 CLI

在回答"如何做好 CLI 人机交互"之前，我们必须先理解一个更基础的问题：为什么偏偏是 CLI？

2.1 文本协议的天作之合

答案其实出奇地简单：LLM 本质上是一个处理文本的概率模型——给它文本，它吐出文本。而 CLI 恰好也是这么工作的。

图2：Token 经济性对比

图2：LLM与CLI通过文本协议实现零成本对接

GUI（图形用户界面）的工作流程是：用户意图 → 坐标定位 → 点击操作 → 触发事件 → API 调用。每一层都是信息损失和延迟的来源。而 CLI 是输入结构化文本 → 输出结构化文本，与 LLM 的工作模式完全一致，不需要任何中间转换层。

2.2 四大核心优势

除了协议匹配之外，CLI 在 AI 场景下还有四大不可替代的优势：

~84%
Token 节省
(渐进式发现 vs 全量注入)
∞
可组合性
(Unix 管道哲学)
0ms
额外延迟
(无渲染管道)

2.2.1 优势一：渐进式发现（Progressive Discovery）

这是 CLI 相对于 API 最被低估的优势之一。

❌ API 方式：全量注入

每次对话，Agent 都需要接收所有工具的完整 JSON Schema 定义。假设你的工具集有 84 个工具，平均每个 Schema 约 185 tokens：

// API 模式：每次对话都注入全部工具定义（不管用不用）
// 总计 ≈ 84 × 185 = 15,540 tokens/轮
// 用户只用了其中 3 个工具 → 浪费 98.2%

⚠️ 每轮对话都要付费加载所有工具定义，即使只用其中 1 个。

✅ CLI 方式：按需查询
// CLI 模式：启动时只需告诉模型有哪些命令
// Agent 需要时才执行 --help 按需查询

$ mytool --help          // ~150 tokens
Usage: mytool <command>

Commands:
  user      User management
  calendar  Calendar operations
  message   Send messages

$ mytool user --help     // ~200 tokens (仅在需要时才消耗)
$ mytool calendar events list --help  // ~250 tokens

// 总 token 消耗 = 实际使用的命令数 × 单个 help 大小
// 使用 3 个命令 ≈ 600 tokens（对比 API 的 15,540）

✅ Token 消耗降低约 96%。这就是 Unix 哲学中 "做一件事并做好它" 在 AI 时代的经济价值。

2.2.2 优势二：训练数据优势

LLM 的训练数据中包含了海量的 shell 命令和 bash 脚本。根据公开数据估算：

数据源占比覆盖内容
GitHub 公开代码约 5%git, docker, npm, make, ffmpeg...
Stack Overflow / 技术问答约 2%命令用法排错、参数组合
技术文档 / 教程约 1.5%官方文档中的 CLI 示例

这意味着 Agent 天生对命令行有相当的"直觉"——它见过海量 git commit -m "..."、docker run -p 8080:80 ...、curl -X POST -d '...' 的用法。而每个 API 的认证方式、请求格式、错误码规范、分页机制都不同，Agent 必须逐个学习。

关键区别：CLI 的协议是通用的（几十年 Unix 标准化），API 的协议是每个都不一样的。

2.2.3 优势三：可组合性（Unix 管道哲学）

# 五个命令像乐高一样拼在一起，一行完成复杂任务
cat access.log \
  | grep "404" \
  | awk '{print $7}' \
  | sort \
  | uniq -c \
  | sort -rn \
  | head -20

这种管道组合能力是 GUI 和 API 都难以实现的。GUI 的应用程序通常是单体式的，应用间通信有限；API 可以组合但每次组合都需要编写胶水代码。而 CLI 的管道是操作系统级的原语——零成本、即时可用。

对 Agent 来说这意味着什么？意味着它可以用同一套推理逻辑来组合任意 CLI 工具，而不需要为每个工具组合学习新的编排方式。

2.2.4 优势四：人机通用性

这是一个经常被忽略但极其重要的优势：开发者在终端测试通过的命令，Agent 可以原封不动地直接执行。

在实际使用 Claude Code / Codex CLI 时，你经常会遇到这样的工作流：你在终端里手动试了一条命令，确认结果正确了，然后让 AI Agent 继续用这条命令去批量处理其他文件。命令完全一样，不需要任何"翻译"或"适配"。

而调用 API 时，程序化的调用方式和浏览器/Postman 中的测试方式往往存在微妙差异（如参数内换行导致错误、Header 大小写敏感等）。

三、核心矛盾：如何兼顾"Agent 友好"与"人类友好"

说到这里，你可能会有一个疑问：

"CLI 对 AI 来说确实很棒，但人类也要用 CLI 啊。交互式提示、彩色输出、终端 TUI（Terminal UI）、进度条动画——这些东西对人类是友好的体验，但对 AI 来说不仅没用，还是负担。难道我们就要砍掉所有这些吗？"

这个问题的答案是：不需要二选一。这正是 Google 的 Justin Poehnelt（Google Workspace CLI 的设计者）在设计 Google Workspace CLI 时提出的核心命题，也是本文最想传递给读者的关键洞察。

3.1 把数据和呈现解耦

Google 提出的解决方案可以用一句话概括：把数据和呈现分离（Decouple data from presentation）。

图3：Google 七大设计原则全景

图3：解耦架构——同一个 CLI 后端，根据调用者身份自动切换呈现方式

核心思路是：

  • CLI 内部只做一件事——生成数据（结构化的 JSON/NDJSON）
  • 呈现层是可插拔的客户端——人类得到交互式 TUI，Agent 得到原始 JSON
  • 不需要维护两套代码库——状态由后端服务管理，CLI 只是轻量传输层
# 人类操作 → 得到漂亮的交互式 TUI 界面
$ a2acli watch --task abc123
╭──────────────────────────────────────╮
│  ✅ Task completed                   │
│  Duration: 3m 12s                    │
│  Status: ████████████████████ 100%  │
╰──────────────────────────────────────╯

# Agent 调用 → 得到干净的 NDJSON 结构化输出
$ a2acli watch --task abc123 --no-tui
{"task":"abc123","status":"completed","duration":192,"progress":1.0}

3.2 自动检测调用者身份

实现这种解耦的技术手段非常成熟，主要依赖以下几种检测策略：

检测方法实现方式用途
TTY 检测os.isatty(sys.stdout.fileno())判断是否连接真实终端
Pipe 检测sys.stdout.isatty() == False判断输出是否被重定向
环境变量NO_COLOR, [APP]_NO_TUI显式禁用交互式特性
Flag 参数--json, --no-tui, --yes显式指定输出格式
飞书 CLI 的实践：支持五种输出格式——JSON、NDJSON、table、CSV、pretty。人类默认看 pretty 格式，Agent 加 --json 就能得到结构化数据。GitHub CLI 更进一步——检测到 stdout 被 pipe 时，自动切换为 tab 分隔格式，去掉颜色转义符和截断限制。

四、Google 的 7 条 CLI 设计原则详解

有了上述理论基础，我们来看具体的设计规范。Google 的 Justin Poehnelt 在发布 Workspace CLI 时同步提出了 7 条面向 AI Agent 的 CLI 设计原则。以下结合实际案例逐一解读。

1 可发现性（Discoverability）——帮 Agent 找到入口

人类会随机探索、读错误信息、搜 Google、问同事。但 Agent 只能从你提供的信息里推断该怎么做。

三条规则：

  • 按功能分组，不按字母排序——Agent 扫描的是结构，不是字母表
  • 显式标注入口点——help 描述里加 (start here) 或 (typical first step)
  • 示例比描述更重要——Agent 会解析示例来推断 flag 的用法
$ mytool --help
Usage: mytool <command>

Commands:
  init        Initialize a new project  ← (start here)
  deploy      Deploy to production
  monitor     Monitor running services
  logs        View application logs

Options:
  --help      Show help
  --version   Show version

Examples:
  mytool init --template node-express    # Create new project
  mytool deploy --env prod               # Deploy to production
  mytool logs --since 1h                 # View recent logs
2 Agent 优先的互操作性（Interoperability）

每个产生数据的命令必须支持 --json 或 --no-tui flag。输出必须是合法 JSON 或 NDJSON，不能混入日志。

保护 Agent 的上下文窗口：默认截断大文本块、脱敏敏感信息；需要完整数据时要求显式加 --full 或 --verbose。

# 默认返回精简结果（保护上下文窗口）
$ mytool tasks list
[{"id":"t1","title":"Fix login bug","status":"open"},
 {"id":"t2","title":"Add dark mode","status":"in_progress"}]
Showing 2 of 47 tasks. Use --limit 50 for more.

# 显式要求完整数据
$ mytool tasks list --full --limit 50
3 配置优先级（Configuration Hierarchy）

严格遵循标准优先级链：

CLI Flag > 环境变量 > 配置文件 > 默认值

Agent 不需要知道 URL 和 token，只需传 --env prod，CLI 自己去找对应配置。

4 错误要给出解决路径（Actionable Errors）

每条错误信息后面加 Hint:，Agent 可以解析来自我纠正。尽早失败：在执行重逻辑之前先验证配置和连接，不要让 Agent 等 30 秒之后才发现 token 不对。

# ❌ 坏的错误信息
Error: database not initialized

# ✅ 好的错误信息
Error: database not initialized
Hint: run 'mytool init' to create the local database
  Or: mytool init --db-path ./data/mydb.sqlite
5 Flag 一致性（Flag Consistency）

同一个缩写在所有命令里必须代表同一个意思。不一致的 Flag 会破坏 Agent 的推理——它在一个命令里学到的规律不能用在其他命令上。破坏性操作必须要求显式 Flag 才能触发。

❌ 不一致✅ 一致
-v: verbose / version / validate-v: 始终表示 verbose
-q: quiet / query / queue--quiet: 始终表示安静模式
6 语义化视觉设计（Semantic Visual Design）

用"语义色彩 token"而非直接用颜色名称：定义 Pass token 对应绿色（成功）、Warn 对应黄色（警告）、Error 对应红色（失败）、Meta 对应灰色（元数据）。不要给描述文字和帮助文本上色——过度上色等于什么都没强调。

7 版本管理与生命周期（Lifecycle Management）

--version 要能用，重要更新时主动提示。优雅处理 SIGINT（Ctrl+C）：不能出现数据损坏，Agent 可能在任何时刻被上层系统打断。写操作记录操作者：从 git config user.name 获取身份并记录——在多 Agent 协作场景下，审计追溯越来越重要。

五、进阶：Agent 时代的五大 CLI 设计哲学

在 Google 7 条原则的基础上，社区还总结出了更深层的五条设计哲学。如果说 Google 7 条是"操作手册"，那这 5 条就是"底层思维模型"。

图4：五大设计哲学框架

图4：Agent时代CLI设计的五大哲学维度

5.1 ① 上下文经济性（Context Economy）

核心诉求：每轮 CLI 调用消耗的 token 要尽可能少，信息密度要尽可能高。

人类友好的输出 (~45 tokens)
╭──────────────────────────────────╮
│  ✓ 3 layers in project           │
│  0: Background (solid)           │
│  1: Photo (image, 80%)           │
│  2: Title (text)                 │
╰──────────────────────────────────╯
Agent 友好的输出 (~25 tokens，信息量相同)
[{"i":0,"name":"Background","type":"solid"},
 {"i":1,"name":"Photo","type":"image","opacity":0.8},
 {"i":2,"name":"Title","type":"text"}]

Token 消耗减少约 45%。单次差异不大，但复杂任务可能调用数十次 CLI，差异累积显著。

5.2 ② 调用经济性（Call Economy）

核心诉求：完成一个任务所需的 CLI 调用轮次要尽可能少。

# ❌ 需要两轮调用（操作 + 查询确认）
$ cli layer move 2 --to 0
{"moved":2,"to":0,"status":"ok"}
$ cli layer list              # Agent 还得再调一次才能确认结果

# ✅ 只需一轮调用（操作 + 结果状态一起返回）
$ cli layer move 2 --to 0
{"moved":2,"to":0,"current_order":["Title","Background","Photo"]}

设计含义：每个状态变更命令的返回值中应包含操作后的关键状态快照，避免"先执行、再查询"的两步模式。

5.3 ③ Cache 友好性（Cache Friendliness）

核心诉求：CLI 输出在状态未变时应保持字面完全一致，以利于 LLM 推理的 prompt cache 命中。

// ❌ 带时间戳 → 每轮都不同 → 从此点开始 cache miss
{"name":"my_project","layers":3,"last_modified":"2026-03-15T21:35:11Z"}

// ✅ 纯结构状态 → 项目没变就字面一致 → cache 命中
{"name":"my_project","layers":3}

很多 Agent 框架在组装每轮上下文时会重新注入工具状态。如果这部分输出带时间戳，每轮都不同，从该插入点开始后面全部 cache miss——这在高频调用场景下的成本影响是巨大的。

5.4 ④ 模型友好性（Model Friendliness）

核心诉求：CLI 设计应尽量贴合训练数据中大量存在的 CLI 范式，降低模型幻觉概率。

// ❌ 非标准命名 → 模型可能幻觉出 --json（因为训练数据中更常见）
$ mytool export --machine-readable

// ✅ 标准 → 贴合高频模式，模型不会猜错
$ mytool export --json

// ❌ 非标准子命令结构
$ mytool do --action=list --type=layer

// ✅ 标准子命令（和 git/docker/kubectl 一致）
$ mytool layer list
Convention over creativity ——在 Agent 时代，遵循约定比追求独特更重要。

5.5 ⑤ Skill-CLI 责任边界（Responsibility Boundary）

核心诉求：确定性的可重复模式封装到 CLI 中；创意性的、依赖上下文的编排交给 Skill 引导 Agent 完成。

图5：Agent 四大认知弱点与对策

图5：Agent→Skill→CLI三层架构及责任边界

# ✅ 适合封装到 CLI（确定性批量操作）
cli batch convert --input "*.png" --format webp --quality 80
# 如果让 Agent 编排：每张图 3 轮 × 100 张 = 300 轮推理循环！

# ✅ 适合 Skill + Agent 编排（依赖上下文的创意任务）
cli project new --width 1080 --height 1080
cli layer add-from-file photo.jpg            # Agent 决定加哪张图
cli filter add brightness -l 0 -p factor=1.3 # Agent 根据图片决定参数
cli draw text --text "Hello" --size 48       # Agent 决定文案

经验法则：如果一个流程每次执行步骤都一样 → 放入 CLI；如果步骤取决于上下文 → 交给 Skill + Agent 编排。

六、人机交互设计的关键细节：防住 Agent 的弱点

了解了宏观原则之后，我们来看看具体的设计细节。Agent 并非万能——它有自己独特的"认知缺陷"，好的 CLI 设计就是要帮 Agent 避坑。

6.1 Agent 的四大认知弱点

弱点表现CLI 应对策略
大小写混淆 grep -a vs grep -A 含义完全不同；Agent 基于 token 概率选错 所有参数必须有长格式 --ascii / --after-context
交互式提示恐惧 Are you sure? [y/N] 对 Agent 是一堵墙 --yes/--no-interactive 跳过所有提示
参数幻觉 Agent 自信地使用不存在的 --smart-mode 枚举约束 + schema 自省 + 严格输入验证
非结构化输出困惑 人类可读的 table 输出对 Agent 来说靠猜 stdout 输出 JSON，stderr 输出状态信息
真实灾难案例：2019 年 AWS CLI v2 将默认 pager 改为 less，导致全球数千个 CI 任务挂起——因为 less 是一个交互式程序，在非 TTY 环境中等待输入永远不会返回。这个教训在今天更加重要：每一个有副作用的命令都必须考虑"如果被 Agent 自动调用会发生什么"。

6.2 干跑（Dry-run）：给 Agent 探索-验证的反馈循环

每个有副作用的命令都应该支持 --dry-run。好的干跑输出不只是"将会做什么"，而是结构化的 diff，精确告知 Agent 什么会被创建、修改或删除。

$ lark-cli calendar event create \
    --title "团队周会" \
    --start "2026-05-15T14:00" \
    --dry-run

{
  "dry_run": true,
  "action": "create",
  "resource": "calendar_event",
  "changes": {
    "created": [{"title":"团队周会","start":"2026-05-15T14:00+08:00"}],
    "modified": [],
    "deleted": []
  },
  "request_url": "https://open.feishu.cn/open-apis/calendar/v4/calendars/primary/events",
  "method": "POST"
}

Lightning Labs 的创新实践：--dry-run 使用专门的退出码（exit code 10），这样 Agent 可以通过退出码区分"干跑成功"和"真正执行成功"，实现更精细的控制流。

6.3 退出码控制：细粒度语义

不要只用 0/1。细粒度的退出码能让 Agent 用 case/switch 直接路由不同的恢复策略：

退出码含义Agent 应对策略
0成功继续执行下一步
1一般错误读 stderr 诊断
2参数错误修正参数后重试
3资源不存在跳过或先创建资源
4权限不足提示用户授权
5冲突/已存在跳过或更新
10Dry-run 成功确认后执行正式操作
重要提醒：退出码一旦发布即为契约（Contract），不可随意修改——就像 Kubernetes v1.18 移除 --export 导致数千 Helm chart 崩溃的教训一样。

6.4 幂等设计：Agent 会重试

Agent 会因为网络超时、任务中断、结果不确定等各种原因重试。命令式操作在重复执行时会报错；声明式操作无论执行多少次结果一致。

# ❌ 命令式：第二次执行报错
$ mytool user create --name john
Created user "john"
$ mytool user create --name john
Error: user "john" already exists

# ✅ 声明式：无论执行多少次，结果一致
$ mytool user ensure --name john
User "john" is ready.
$ mytool user ensure --name john
User "john" is ready.

# 或者使用条件标志
$ mytool user create --name john --if-not-exists

kubectl apply 是声明式设计的教科书级案例。飞书 CLI 则更进一步——+messages-send 支持 --idempotency-key 参数：Agent 传入唯一标识符，即使命令被重复执行，服务端也只会处理一次。

七、实战评估：谁做得好，谁还需要改进

7.1 飞书 CLI 评估

✅ 做得好的
  • noun-verb 层级命令结构清晰，Agent 可树搜索探索
  • 三层架构（REST API → SDK → CLI），Agent 按需选择抽象层级
  • schema 命令提供完整 API 自省能力
  • 五种输出格式（JSON/NDJSON/table/CSV/pretty）
  • 按域申请权限（最小权限原则），不足时自动提示修复方案
  • --yes 明确标注为"AI Agent 模式"
⚠️ 可改进的
  • 非 TTY 下没有自动切 JSON（需要手动加 --json）
  • 退出码没有文档化的细粒度语义
  • --idempotency-key 应该更广泛地应用到其他写操作

7.2 钉钉 CLI 评估

✅ 做得好的
  • --yes 参数描述为"跳过确认提示（AI Agent 模式）"——语义自描述，Agent 一看就懂该什么时候加
  • --mock 参数方便调试和测试
  • 帮助文本全中文（对中文 LLM 更友好，减少中英混杂的幻觉风险）
  • 批量熔断机制防止 Agent 失控循环调用
⚠️ 可改进的
  • 命令只有两层，缺少 shortcut 快捷层
  • 没有 schema 自省命令
  • 输出格式只有三种（JSON/Table/Text），缺少 NDJSON 流式输出
  • 帮助文本缺少可直接复制粘贴的使用示例

7.3 用五大哲学评估 CLI-Anything 项目

原则评分具体问题
上下文经济性❌ 差默认输出人类友好格式，JSON 只是 opt-in；499 行 repl_skin.py 全是边框/emoji/彩色——Agent 不需要任何一行
调用经济性⚠️ 中layer move 只返回 {"moved":2,"to":0}，不含新排列顺序；Agent 想确认结果还得再调一轮
Cache 友好性❌ 差代码里随意嵌入 datetime.now().isoformat()，每次快照输出都不同
模型友好性✅ 好Click 框架 + 标准子命令结构 + --json flag；但不是刻意为 Agent 设计的，只是 Python CLI 的通用最佳实践
Skill-CLI 责任边界❌ 差没有任何 batch 命令；REPL 交互模式却是默认入口——Unix 哲学反对它，Agent 时代更不合适

九、总结与展望

2026 年最好的 CLI，不是终端界面最漂亮的那些，

而是当人类输入命令和当 Agent 编程调用时，同样运行良好的那些。

回顾全文，我们的核心论点可以概括为三层：

第一层（为什么是 CLI）：LLM 是文本概率模型，CLI 是文本协议——两者天然匹配。加上渐进式发现的 Token 经济优势、训练数据的先验知识红利、Unix 管道的可组合能力、以及人机通用的互操作性，CLI 成为 AI 时代能力分发的最优解。

第二层（如何兼顾两种用户）："数据和呈现解耦"是关键架构思想。同一个 CLI 后端，通过检测 TTY/pipe/环境变量自动切换呈现层——人类得到漂亮的 TUI 和彩色表格，Agent 得到干净的 JSON 结构化数据。不需要维护两套代码库。

第三层（具体怎么做）：Google 的 7 条设计原则提供了操作框架，而社区总结的五条设计哲学（上下文经济性、调用经济性、Cache 友好性、模型友好性、Skill-CLI 责任边界）提供了底层思维模型。配合本文整理的 20 项 Checklist，你可以系统性地审查和改进你的 CLI 工具。

9.1 这不仅是 CLI 的问题

这套框架的适用范围远超 CLI。随着 Agent 介入各种工具链，SDK、API、内部平台工具迟早都会被 Agent 调用。"对人类友好"和"对 Agent 可用"将成为每个工具必须同时满足的要求。

你可以用这五个问题来审视任何面向 Agent 的接口：

#问题优化方向
1你的输出占用 Agent 多少上下文？上下文经济性 → 默认精简 JSON
2Agent 需要几轮调用才能完成任务？调用经济性 → 返回操作后状态快照
3你的输出在状态不变时能否保持一致？Cache 友好性 → 避免易变元数据
4你的接口设计贴合模型的先验知识吗？模型友好性 → 遵循业界惯例命名
5哪些逻辑该你做，哪些该让 Agent 做？责任边界 → 确定性与创意性分离

9.2 GUI 的不可替代场景

在大力推崇 CLI 的同时，我们也必须承认 GUI 在以下场景中的不可替代性：

  • 视觉设计任务：UI 架构设计、数据可视化、视频编辑、图像处理——文本表示空间关系极其笨拙
  • 探索性交互：新手入门、临时单次操作——GUI 的可见即可操作大幅降低认知门槛
  • 实时预览需求：需要即时视觉反馈的创意工作——"所见即所得"无可替代
  • 非技术用户：对没有命令行经验的用户，GUI 仍然是唯一可行的入口

TUI（Terminal UI）框架如 Charm / Bubbletea 提供了一个有趣的中间地带——在终端内实现结构化的视觉呈现，保留 CLI 的可组合性和脚本化能力，同时提供组织布局、颜色、键盘导航等增强体验。

9.3 最终结论

也许，CLI 一直就没退场，只是大家习惯了更花哨的界面，慢慢把它当成了老古董。现在 AI 来了，而它刚刚好。

就像蒸汽机车和高铁动车同框的照片——不是谁取代了谁，而是每一种技术都有它合适的场景。AI 时代不是 CLI 的复兴，而是 CLI 找到了它最合适的搭档。
